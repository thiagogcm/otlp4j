# Performance baselines

This directory holds the committed JMH baseline that the Phase 0 exit criteria require. Each
`baseline-<date>.json` is a full JMH result set captured with the GC profiler, so it records both
throughput and per-operation allocation for the receive-forward-export path and the codec
marshalling path. Phase 2 compares a fresh run against the newest baseline here to attribute any
change to the codec or the transport.

## How a baseline is produced

Build the shaded uber jar and run the whole harness with the GC profiler, writing JSON:

```
just bench-baseline
```

which expands to the two steps the recipe runs:

```
./mvnw -B -Pbench -pl otlp4j-benchmarks -am package -DskipTests
java -jar otlp4j-benchmarks/target/benchmarks.jar -prof gc \
    -rf json -rff otlp4j-benchmarks/baselines/baseline-<date>.json
```

The `bench` profile keeps the benchmark module out of the default reactor, so `./mvnw verify`
never builds it. The uber jar lists and runs its benchmarks on its own
(`java -jar otlp4j-benchmarks/target/benchmarks.jar -l`); the annotation processor emits
`META-INF/BenchmarkList` and the shade `ServicesResourceTransformer` merges the gRPC provider
service files so a `host:port` channel resolves without `ProviderNotFoundException`.

Produce these numbers on a quiet machine, never on shared CI: JMH results from a contended runner
are not trustworthy baselines, which is why the recipe is documented but the committed file is
generated by the engineer running Phase 0.

## Run parameters (the documented short run)

The fork, warmup, and measurement counts are pinned as annotations on the two benchmark classes
rather than passed on the command line, so a plain `just bench` or `just bench-baseline` already
executes the short, repeatable run and needs no extra flags:

- `@Fork(1)`
- `@Warmup(iterations = 3, time = 1)` (three one-second warmup iterations)
- `@Measurement(iterations = 5, time = 1)` (five one-second measurement iterations)
- `@BenchmarkMode({Throughput, AverageTime})` on both classes

Both benchmark methods are parameterized:

- `ReceiveForwardExportBenchmark` over `protocol` in {`GRPC`, `HTTP`} and `size` in {`small`,
  `large`}, giving the four end-to-end combinations.
- `CodecMarshallingBenchmark` over `signal` in {`TRACES`, `METRICS`, `LOGS`} and `size` in
  {`small`, `large`}.

`small` is a one-item batch; `large` is a 500-item batch (`BenchmarkPayloads.LARGE_ITEM_COUNT`).
With these settings the full GC-profiled baseline completes in a few minutes, well under any
practical time budget, so no further trimming of iterations or forks is applied. If a future run
must be shortened further, override on the command line (for example `-f 1 -wi 1 -i 3`) and note
the override alongside the resulting file.

## What to record alongside each file

Note these with every committed baseline so a later comparison is apples to apples:

- JDK vendor and version (`java -version`).
- CPU model and core count, total RAM, and OS/kernel.
- Whether the machine was otherwise idle.
- Any command-line override of the pinned run parameters.

## How Phase 2 compares against a baseline

Run the identical jar with the identical flags on the same machine, write a new dated JSON, and
diff the two on the fields that matter:

- `primaryMetric.score` under `Mode = thrpt` for throughput (higher is better).
- `secondaryMetrics."gc.alloc.rate.norm".score` for bytes allocated per operation (lower is
  better). This is the allocation half of the deliverable the payload redesign targets.

Compare like for like: same `protocol`/`size` (or `signal`/`size`) parameter tuple, same benchmark
mode. A meaningful Phase 2 win shows a lower `gc.alloc.rate.norm` on the codec marshalling
benchmark and, ideally, higher end-to-end throughput at unchanged allocation.

### baseline-2026-07-06.json headline numbers

Throughput is from the `Throughput`-mode results, latency from the `AverageTime`-mode results, and
allocation is `gc.alloc.rate.norm` (bytes per operation). Numbers are captured on a developer
laptop under WSL2 and are a relative baseline for Phase 2 regression tracking, not an absolute
performance claim.

| gRPC | large | 0.335 ops/ms | 3.17 ms/op | 3.91 MB/op |
| HTTP | small | 0.730 ops/ms | 1.54 ms/op | 251 KB/op |
| HTTP | large | 0.305 ops/ms | 3.08 ms/op | 4.77 MB/op |
