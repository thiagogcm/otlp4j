# OTel-Arrow Rust backend feasibility for otlp4j through Java FFM

## 1. What reusable Rust libraries, native boundaries, versions, and licensing actually exist?

### Takeaway

**Verdict: feasible as a custom, batch-oriented native codec and columnar processing backend, not a drop-in Java model backend.** This checkout contains genuine Rust OTLP bytes, OTLP message, OTAP Arrow-record, and OTAP IPC/protobuf conversion APIs, separately from an embeddable collector runtime. ## 2. Which conversions and signals are supported, and how faithful is the model boundary?

### Takeaway

Rust supports logs, traces and standard OTLP metric kinds in both directions between protobuf bytes/messages and a signal-specific **set** of Arrow RecordBatches. It also independently implements OTAP `BatchArrowRecords` protobuf/IPC production and consumption, with persistent schema/dictionary state. Semantic equivalence is the goal, but exact Java object identity, grouping, repeated-field order, absent/default presence, duplicate multiplicity and byte-for-byte protobuf preservation are not demonstrated by the existing equivalence tests. **Go functionality is distinct.** Go's `go/pkg/otel/arrow_record/producer.go` converts Collector `pmetric.Metrics`, `plog.Logs`, and `ptrace.Traces` through `BatchArrowRecordsFromMetrics/Logs/Traces`; its consumer returns Collector pdata. Those are not Rust types or APIs. Rust nevertheless has its own real Producer/Consumer, builders and conversions, rather than merely importing or invoking Go. Go Collector distribution inclusion since v0.104.0 is evidence for the Go components, not proof of Rust native ABI stability or equal production maturity. [go/README.md:3-20,23-51][go-readme] [go/pkg/otel/arrow_record/producer.go:204-273][go-producer] [README.md:63-66][root-readme] [producer] [consumer]

**Representation and coverage.** `OtapArrowRecords` is a Rust enum with `Logs`, `Metrics`, and `Traces` variants. Logs have 4 payload slots, traces 8, metrics 19; unused payloads may be absent. Metrics' nineteenth slot is `MultivariateMetrics`, which the OTLP builder explicitly does not implement; standard conversion builds 18 possible payload types. Standard metric kinds are empty, gauge, sum, histogram, exponential histogram and summary. Profiles are not an OTAP variant even though generated profile protobuf sources exist; root README calls profiles future work. [otap.rs:39-48,73-95][otap-records] [raw_batch_store.rs:84-128][batch-slots] [encode/mod.rs:971-991][encode-records] [otlp/metrics.rs:51-60][metric-kinds] [README.md:106-120][root-readme]

**Metrics semantics are implemented, not merely promised.** Builder traversal retains temporality and monotonicity, metric metadata, datapoint attributes, integer/double number values, exemplars and filtered attributes, explicit bounds/counts and optional sum/min/max, exponential histogram scale/zero-count/zero-threshold and positive/negative buckets. Reverse metrics code uses signal-specific datapoint/exemplar encoders. A wrapper must preserve these distinctions rather than flatten metrics into one value/timestamp table. [encode/mod.rs:763-810,845-902][encode-records] [otlp/metrics.rs:18-37,45-60][metric-kinds]

**Resource/scope and parent semantics.** Resources/scopes are embedded struct fields in root tables, with attributes in separate payloads, not standalone resource/scope tables. `resource.id` and `scope.id` are local join identifiers, not an application's persistent entity identity; the spec says no single table owns their valid ID set. Trace OTAP row IDs are also distinct from real `trace_id`, `span_id`, and `parent_span_id`. Trace builders separately retain real IDs, parent span ID, flags, trace state, status and dropped counters while assigning local u16 IDs and u32 child event/link IDs. [otap-spec.md:745-759][otap-spec] [encode/mod.rs:53-63,95-120,127-158][encode-records]

**Adaptive schema, sorting and state.** Optional columns are omitted when unused; legal physical types can include native and dictionary variants. Transport encoding can sort root/child tables and delta/quasi-delta encode IDs, flagged by metadata. `Producer` manages one active producer per payload type, replaces it when schema changes, increments batch/schema IDs, and writes schema/dictionary messages as required. `Consumer` retains readers by schema ID and removes older reader state for the same payload type. Subsequent BAR payloads can contain only incremental IPC bytes, not a schema or complete dictionary. Therefore processing them out of order or with a fresh consumer can fail. `Producer::reset_streams` exists to restart streams for independent consumption, but a fresh producer per standalone call is the simpler initial design. [otap-spec.md:274-356,761-778][otap-spec] [otap.rs:157-202][otap-records] [producer.rs:23-40,111-139,244-331][producer] [decoder.rs:68-114][consumer]

**Synchronous versus asynchronous ownership.** The codec decoder/encoder methods and pdata conversion/Producer/Consumer APIs are synchronous. `PdataDecoder` and `PdataEncoder` require `Send`, not `Sync`; exclusive mutable access is part of their usage. Prepared output can borrow encoder scratch only during synchronous use; `EncodeOutput::into_bytes` detaches it before an await/next mutable access. Raw protobuf views borrow `&[u8]` and some internal field-range caches use `Cell`, so blanket thread-safe shared-view assumptions are unjustified. The full engine favors local async thread-per-core instances. [codec-decoder] [codec-encoder] [pdata-codec/README.md:81-93][codec-readme] [views/otlp/bytes/traces.rs:45-74][raw-traces] [engine-readme]

**Not zero-copy row-to-column conversion.** The raw view can traverse existing OTLP bytes without materializing Prost objects, but Arrow builders allocate and append columns. Conversely OTLP emission serializes bytes. Producer's IPC serialization copies its output buffer into a new vector, and consumer initialization clones its cursor bytes. Zero-copy C Data sharing applies to already-built Arrow buffers, not the entire Java-record to OTLP to Arrow to Java-record chain. [encode/mod.rs:53-79,127-158][encode-records] [producer.rs:111-127][producer] [decoder.rs:28-36][consumer] [arrow-ffi]

**Compatibility with otlp4j is semantic, not representational.** otlp4j's `ResourceSpans`/`ScopeSpans` and `ResourceMetrics`/`ScopeMetrics` are Java records with nested immutable-copy lists. Resource/scope are Java value records, not Arrow buffers. An Arrow C Data export does not supply those existing Java records, their builders or Java object identity; reconstructing them still requires grouping, joins and object allocation. LogsData and ExportLogsServiceRequest are wire-compatible in the inspected Rust generated source because both consist of repeated resource logs at protobuf tag 1, illustrating why OTLP protobuf is the safest initial interop boundary. Do not generalize that to JSON, gRPC framing, or arbitrary future message definitions without tests. **Preservation limits and test caveats.** Existing equivalence helpers explicitly normalize absent values to defaults, erase default resources/scopes, sort and deduplicate vectors with `BTreeSet`, and compare split singleton messages as sets. Passing them does not prove order, group boundaries, presence or duplicate multiplicity preservation. The builder returns entirely empty metrics records when no metrics exist, showing that empty structural groups require explicit policy/testing. Checked u16/u32 counters return overflow errors; standard u16 roots/groups cannot simply accept unbounded Java batches. OTLP `ProtoBuffer` is capped at 256 MiB and `ConversionOptions` only sets an OTLP encoded-size limit; this does not bound input Arrow memory or all decode allocations. ### Inferences

- Exact OTLP unknown-field preservation should not be promised: the Arrow mapping enumerates known fields and the generated structs have no unknown-field storage. An unchanged encoded pass-through can preserve original bytes, but decode/convert/re-encode is a different contract. Treat unknown fields, new enum values, duplicate singular protobuf fields and future protocol additions as explicit conformance cases. [encode-records] [proto-logs] [proto-logs-request] [raw-traces]
- Resource/scope value equality and Java reference identity need separate policies. Equal-valued groups can still be separate input groups; OTAP local IDs must not be substituted for existing application's resource keys. Preserve schema URLs, scope name/version/attributes and dropped counters in all comparisons. [otap-spec] [java-traces] [java-metrics] [java-resource] [java-scope]
- Timestamp conversions deserve boundary tests: builder casts OTLP unsigned nanoseconds to signed Arrow nanoseconds, and span duration is computed by signed subtraction. Valid common timestamps should work, but large uint64 values, backwards timestamps and overflow cannot be assumed safe/lossless solely from the README. [encode/mod.rs:134-141,853-854,874-877][encode-records]
- Columnar transforms must coordinate every related payload and parent ID, not mutate only the root table. Standard pdata contains synchronous concatenate/split and transport-ID logic, which is a stronger starting point than rewriting all joins in Java. [otap.rs:157-202][otap-records] [otap/transform/concatenate.rs:159-225][concatenate] [otap/transform/split.rs:43-67][split]

### Gaps

- Exact end-to-end field compatibility with all otlp4j record types, null/default conventions, attributes and profiles awaits the separate Java analysis and a shared conformance corpus. No claim of full drop-in compatibility is justified by this Rust-only audit.
- Strict codec validation checks protobuf structural validity with Prost, not necessarily every OpenTelemetry semantic constraint, valid enum value, identifier length, or application-specific invariant. Invalid/absent IDs and optional/default fields need differential tests.
- Existing raw view best-effort decoding can silently treat malformed nested content as iterator exhaustion; the upstream documentation explicitly warns about this. Defaulting the FFM boundary to strict validation is recommended. [pdata-codec/README.md:138-149][codec-readme]
- No claim is made that the canonicalization-induced blind spots are actual production data-loss bugs. They are limitations of what the inspected tests establish. Byte identity, repeated-item multiplicity, empty groups and preservation of newer OTLP fields require independent assertions.

## 3. What should a concrete native FFM wrapper and minimum proof of concept look like?

### Takeaway

Build a separate commit-pinned Rust `cdylib` with a small, versioned C ABI: bytes and opaque batch/session/buffer handles first, optional Arrow C Data access second. Keep otlp4j's public row-oriented Java model and collector lifecycle in Java initially. A byte-oriented OTLP-to-OTAP codec proof is low-risk relative to replacing the model, while a reusable native Arrow batch provides the best opportunity to avoid repeated conversions. This is a proposed architecture inferred from the actual public conversion and stream APIs, not existing code. [pdata-api] [conversions] [producer] [consumer] [arrow-ffi]

### Cited Findings

The boundary below is **proposed**, not an upstream ABI. Its justification is the public synchronous pdata conversion/stream APIs, existing Rust `Result` errors, owned `Bytes` output, mutable stream state, and dependency Arrow release mechanisms. `OtlpStrictDecoder` and `OtlpEncoder::new` are private; a minimal downstream wrapper should call public Prost models plus public `encode_*_otap_batch` and `ProtoBytesEncoder`, or use the public codec registry/service instead of attempting to instantiate those private helpers. [otlp-codec] [codec-api] [codec-decoder] [codec-encoder] [conversions]

| Proposed C operation | Contract and Rust implementation |
| --- | --- |
| `oa_abi_version`, `oa_build_info` | Report wrapper ABI major/minor, upstream commit, Arrow version and supported signals/features. Never expose Rust layout/version as ABI. |
| `oa_otlp_decode(signal, ptr, len, options, out_batch, out_error)` | Strictly decode a complete uncompressed OTLP protobuf request via Prost, then public `encode_*_otap_batch`. Input borrowed only for this call; initial implementation copies where necessary. Return an opaque owner of `OtapArrowRecords`. |
| `oa_batch_encode_otlp(batch, out_buffer, out_error)` | Reusable signal encoder plus `ProtoBuffer`, or bounded conversion. Return independently owned output, not a pointer into scratch that the next call invalidates. Document whether the batch can be normalized/mutated. |
| `oa_batch_encode_otap_standalone(batch, out_buffer, out_error)` | Fresh Producer for this call, produce BAR, Prost-encode it. Includes complete IPC schema/dictionary state and can be decoded by a fresh consumer. |
| `oa_otap_decode_standalone(signal, ptr, len, out_batch, out_error)` | Prost-decode BAR, use fresh Consumer, assemble signal-specific records via `from_record_messages`. Reject incomplete/incremental IPC input. |
| `oa_batch_signal`, `oa_batch_item_count`, `oa_batch_payload_count/list` | Identify the whole batch and present payload types. Metrics item count is datapoints, not metric objects. |
| `oa_buffer_data`, `oa_buffer_len`, `oa_buffer_release` | Opaque owned Rust buffer handle. Java reads/copies a native `MemorySegment`; only Rust releases Rust allocations. |
| `oa_batch_release`, `oa_error_message`, `oa_error_release` | Explicit deterministic lifetime/error ownership; no Rust `String`, `Vec`, `Result`, panic or trait object crosses C. |
| Optional `oa_producer_create/produce/reset/release`, `oa_consumer_create/consume/release` | Long-lived stateful stream sessions, one signal/session, sequential access, ordered BAR delivery. These are not the standalone codec contract. |
| Later `oa_batch_export_payload_cdata(batch, payload_type, out_array, out_schema)` | Export one entire payload RecordBatch as a struct array plus ArrowSchema. Keep schema/field metadata and dictionaries; retain native ownership until release. |
| Later `oa_batch_import_payload_cdata(batch, payload_type, array, schema)` | Explicit transfer of Arrow ownership, lifetime and release callbacks; schema-validate through `OtapArrowRecords::set`. Trusted cooperating pointers only. |

**Input/output definitions.** A protobuf request here is the message body, not gRPC's compression flag/length prefix, an HTTP envelope, JSON, or ExportServiceResponse. Signal codes and options should use explicit fixed-width C types and named constants, while pointer lengths can use documented `size_t`. Validate null/length consistency, overflow and configured message-size limits before forming slices. Opaque handles can use checked integer IDs/generations to make stale-handle errors diagnosable; avoid exposing arbitrary `Box<T>` pointers as if Rust layout were public. These are boundary design requirements derived from the signal-tagged bytes and owned/borrowed output contracts. [otlp-api] [codec-encoder] [proto-logs-request]

**Error and panic handling.** Use numeric status codes plus explicitly owned UTF-8 error text, classify malformed protobuf, wrong signal, invalid OTAP schema, u16/u32 overflow, output limit and internal failure. Initialize all out parameters to empty before work. Wrap exported functions in an unwind barrier for recoverable Rust panics and never unwind into Java. This does not contain OOM aborts, invalid pointers or all upstream native faults; pointer and lifetime correctness remain mandatory. Discard/reset a stateful producer/consumer after an error unless recovery has been explicitly tested. [encode-errors] [codec-decoder] [producer] [consumer] [arrow-ffi]

**Threading and ownership.** Start with thread-confined native session handles, with serialized calls and no Java callbacks/upcalls. `Send` does not mean concurrent `&mut` access is legal. Batch/buffer releases must be exactly once and cannot race reads or codec operations. Return independently owned encoded buffers or caller-owned output copies; never expose the codec's scratch as an indefinitely valid MemorySegment. For Arrow exports, the allocation must live until the C release callback, independently of the Java arena storing the small ArrowArray/ArrowSchema structs. Keep the library loaded while any handle or release callback is live. [codec-decoder] [codec-encoder] [raw-traces] [arrow-ffi] [arrow-stream]

**Arrow C Data versus C Stream.** C Data export can share already-created Arrow buffers without serialization, but one pair represents one payload, not an entire OTAP star schema. A single C Stream has one schema, whereas OTAP has multiple payload schemas and schema resets. Export one C Data pair per payload or one C Stream per payload/session with explicit payload identity and coordinated lifetime. Do not put heterogeneous logs/attributes/exemplars batches into one generic Arrow stream. Converting into Java's existing records still requires allocations; a genuinely columnar Java API would need a new `NativeTelemetryBatch` abstraction or Arrow vectors alongside, not secretly underneath, the current model. [batch-slots] [otap-records] [otap-spec] [arrow-stream] [java-traces] [java-metrics]

### Inferences

#### Minimum proof of concept

1. **Logs-only, bytes-to-bytes standalone round trip:** Java serialized OTLP logs request -> strict Rust decode -> OTAP batch -> fresh Producer -> BAR bytes -> fresh Consumer -> OTLP bytes -> Java decode. Expose only ABI version, one standalone encode, one standalone decode, owned buffer access/release and error release. This isolates codec feasibility without collector lifecycle, Arrow Java dependency, unsafe input C Data or Java model redesign. The proposed implementation path is directly supported by the inspected APIs. [otlp-codec] [producer] [consumer] [conversions]
2. **Extend to traces and all five standard metric kinds:** test metric metadata, temporality, monotonicity, flags, exemplars/filtered attributes, bounds/counts, optional sum/min/max, scale/zero-threshold/negative buckets, summaries, trace status/links/events/flags and parent relationships. Assert signal and item counts, multiplicity and policy-defined grouping/presence, not only upstream set-based equivalence. [metric-kinds] [encode-records] [canonical]
3. **Retain native batch handles:** decode once, inspect counts, perform one public batch transform, and encode in either wire form. Benchmark Java codec-only, FFM standalone and retained-batch paths across tiny/large batches. Native benefit is plausible when data stays columnar over multiple operations, not guaranteed when Java serializes/materializes around every call. [conversions] [concatenate] [split] [java-traces]
4. **Stateful OTAP stream proof:** keep separate producer/consumer sessions, process multiple schema/dictionary-changing batches in order, reconnect/reset, and test malformed/truncated batches followed by valid ones. Never retry a later incremental BAR into a fresh consumer as though it were standalone. [producer] [consumer] [codec-readme]
5. **Optional C Data proof:** export the logs root plus its attribute payloads without copying their buffers; read columns from Java, then release deterministically. Verify dictionary types, schema metadata and lifetimes. Only after that investigate import and generic Java columnar/model adapters. [batch-slots] [arrow-ffi] [arrow-stream]

#### Likely adaptation cost and architectural fit

| Integration choice | Relative cost | Assessment |
| --- | --- | --- |
| Standalone byte codec provider | Lowest | Straight public Rust conversion/stream dispatch plus C ABI safety, Java FFM loader, packaging and conformance tests. Useful for adding OTAP wire support. |
| Stateful OTAP transport codec | Moderate | Requires stream-session ownership, ordering, reset/reconnect and failure policy in addition to the basic wrapper. |
| Native Arrow batch transform provider | Moderate to high | Retained batch handles and multi-payload semantics, optional query integration. Most credible path to columnar processing benefit. |
| Arrow C Data Java facade | High | Zero-copy buffer lifetime, callbacks, dictionaries, metadata, multiple schemas and explicit columnar API. Does not remove OTLP conversion work. |
| Existing otlp4j model transparently backed by Rust | Very high | Existing nested immutable Java records are not Arrow layouts. Requires a new facade/model design or repeated reconstruction; per-field FFM calls are an undesirable default. |
| Entire native collector inside the JVM | Highest and separate scope | Need managed runtime threads, lifecycle/shutdown, networking, acknowledgement/backpressure, telemetry, configuration and error propagation. Rust embedding examples are for Rust binaries, not a stable foreign ABI. |

These are qualitative engineering estimates inferred from the APIs and representations, not implementation timelines or validated performance results. A Java callback adapter for every Rust view trait would create many fine-grained upcalls, complicated borrowed lifetimes and reentrancy. Prefer coarse batches/bytes or a dedicated native columnar model rather than that route. [views-readme] [java-traces] [java-metrics] [engine-readme]

### Gaps

- Unsupported assumptions to reject: an existing native library/header; stable upstream Rust or C ABI; Go Collector pdata APIs available in Rust; one RecordBatch containing all telemetry; standalone decoding of every BAR; automatic drop-in Java model compatibility; complete protobuf byte/unknown-field preservation; profiles support; implemented multivariate metrics; thread-safe concurrent mutable sessions; entirely zero-copy OTLP conversion; guaranteed performance wins from FFM.
- No selected Java Arrow/C Data library or FFM Arrow layout implementation was evaluated here. The precise Java FFM adapters, native-access launch flags, JDK compatibility and packaging mechanism should follow the parallel Java/lance4j research.
- Native binary size, build time, license closure, upstream upgrade effort and how much unconditional DataFusion/Tokio/Tonic/Nix baggage can be removed were not measured. Do not promise a lightweight dependency-free shared library from the current pdata manifest.
- A new foreign boundary needs fuzzing and memory-safety testing in addition to upstream Rust tests. Invalid native pointers cannot be made safe by ordinary protobuf/schema validation, so imported C Data should be restricted to trusted cooperating code.
